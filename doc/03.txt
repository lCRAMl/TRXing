# 26. Konfiguration

Alle variablen technischen Daten gehören in Konfigurationsdateien.

Mindestens:

```text
config/
├── pallets.json
├── pallet_patterns.json
├── suction_cups.json
└── vacuum_defaults.json
```

Keine technischen Produktdaten in GUI-Code.

Keine Palettendimensionen als magische Zahlen.

Keine Saugerdurchmesser als magische Zahlen.

Keine Herstellerkräfte als magische Zahlen.

---

# 27. Config-Service

Die GUI darf nicht direkt:

```python
json.load(open(...))
```

verwenden.

Stattdessen:

```text
SettingsService
      │
      ├── get_pallets()
      ├── get_patterns()
      ├── get_suction_cups()
      └── get_vacuum_defaults()
```

Die Referenzarchitektur verwendet ebenfalls eine zentrale typisierte Settings-Schicht mit Defaults und Validierung.

Validiere Config-Dateien beim Start.

Fehlerhafte Einträge:

* sauber melden
* nicht die gesamte Anwendung unkontrolliert abstürzen lassen
* wenn möglich mit Default/Recovery-Verhalten arbeiten

# 28. DTO-Design

DTOs sind die Schichtgrenze zwischen Engine, Services und GUI.

Beispiele:

```python
PackageSpec
PalletSpec
PalletPatternSpec
Placement
PalletResult

SuctionCupSpec
VacuumPlateSpec
SuctionPlacement
VacuumInput
VacuumResult
```

Alle DTOs:

```python
@dataclass(frozen=True, slots=True)
```

soweit sinnvoll.

DTOs enthalten Daten, nicht Verhalten.

---

Beispiel:

```python
class PackageService:

class PalletService:

        ...
```

```text
PalletOptimizer
VacuumCalculator
LeakageModel

```

noch deren interne Implementierung.

# 30. Gemeinsamer App-State

Erzeuge einen zentralen, kleinen Application State.

Beispielsweise:

```text
current_package
selected_pallet
selected_pattern
selected_suction_cup
current_vacuum_plate
```

Nicht jeden Zustand über Signals von Tab zu Tab durchreichen.

Aber:

Der State darf keine GUI-Widgets enthalten.

Beispiel:

```python
@dataclass
class AppState:
    package: PackageSpec | None
    pallet_id: str | None
    pattern_id: str | None
    suction_cup_id: str | None
```

Änderungen erzeugen fachliche Events bzw. Service-Notifications.

# 32. Keine Blockierung bei Parameteränderungen

Bei kleinen Änderungen wie:

```text
Paketbreite
Paketgewicht
Saugeranzahl
Plattengröße
```

kann automatisch neu gerechnet werden.

Aber:

* Debounce verwenden
* z.B. 100–300 ms
* nicht für jeden einzelnen Tastendruck einen CPU-Job starten
* laufende veraltete Jobs abbrechen/invalidieren

Beispiel:

```text
Benutzer tippt:

100
1000
10000

nicht:
3 separate teure Berechnungen

sondern:
Debounce
→ eine Berechnung
```

# 45. Vorgehensweise für Claude Code

Arbeite tatsächlich schrittweise.

Nach jedem Meilenstein:

1. Dateien erstellen/ändern
2. Anwendung starten bzw. Tests ausführen
3. Fehler beheben
4. Architekturregeln prüfen
5. erst dann zum nächsten Meilenstein gehen

Nicht zehn Komponenten gleichzeitig halb implementieren.

Jeder Meilenstein soll einen technisch funktionsfähigen Zustand hinterlassen.

Erzeuge zunächst das Running Skeleton vollständig.

Danach implementiere die Fachlogik schrittweise.

Bei Architekturentscheidungen gilt:

**Wartbarkeit, Testbarkeit, Austauschbarkeit und Debugbarkeit haben Vorrang vor maximal kurzer Implementierung.**

Keine unnötige Überarchitektur wie Microservices, Netzwerk-APIs oder Datenbankserver. Das Programm ist eine lokale Desktop-Anwendung.

Die Architektur soll groß genug sein, um langfristig viele Berechnungs-Module aufzunehmen, aber nicht mit für dieses Projekt unnötigen Komponenten aus dem Referenzprojekt belastet werden.
